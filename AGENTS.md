# AGENTS.md — rules for Devin (and humans) working in this repo

This repo is an internal-tools platform. Apps are **config files composed from reusable blocks**, not hand-written pages.

## Layers (imports only flow downward — enforced by `npm run boundaries`)
| Layer | Path | What lives here |
|---|---|---|
| L0 platform | `src/platform/` | users/roles, RBAC, hash-chained audit, PII masking, action pipeline (reason codes → guards → idempotency → maker-checker → execute → audit), approvals, validation |
| L2 connectors | `src/connectors/` | typed data sources (`TableSource`) with PII field tags; external connectors (Stripe, KYC vendor — mocked) |
| L3 blocks | `src/blocks/<name>/` | `manifest.ts` (zod config schema + use-when/not-for + guarantees) and a React component |
| Apps | `src/apps/<slug>/app.ts` | one `defineApp({...})` call: permissions, actions, pages → blocks |
| Portal | `src/app/` | Next.js routes: gallery, generic app renderer, approvals, audit, catalog, request intake |

## Hard rules
1. **Never bypass the platform.** Apps never touch the DB or connectors directly; every mutation is an `action` in `app.ts` and runs through `runAction`.
2. Every app declares `permissions.view`. Anything moving money, touching PII, or changing prod config needs `reasonCodes` and, above a threshold, an `approval` rule.
3. Mark PII fields in the connector (`piiFields`). Never log PII in audit `details`.
4. Synthetic data only. No real customer data, secrets or vendor keys in the repo.
5. Prefer the **lowest rung** of the customization ladder and justify rung ≥ 4 in the PR:
   1) block config → 2) page/block composition → 3) app `handlers` (app-local logic) → 4) new connector/source → 5) extend a block (new optional config, backwards compatible) → 6) new block (via `create-block` skill).
6. When a need isn't covered by any block, build it app-locally (handler) and add a row to `GAPS.md`. Second occurrence → propose extraction. Third occurrence, or anything compliance-critical → new block.

7. **Blocks and the platform stay domain-agnostic.** No source names, field names, thresholds or status vocabulary in `src/platform/`, `src/blocks/` (outside manifest examples) or portal routes. Put them in app config (e.g. `review-queue.badges`, approval `when`) or the `SourceDef` (`fields[x].tones`). A block option is justified only if a second app could plausibly use it with different values. `npm run boundaries` rejects source names in shared code.
8. **Style with the shared design tokens.** Use the classes and colours in `src/app/globals.css` (`card`, `card-title`, `eyebrow`, `btn btn-sm btn-primary|secondary|danger`, `input`, `badge` + `TONE_CLS`, `table-head`, `chip`, `link`, `brand-*`). Don't hard-code new palettes or one-off button/card styles in blocks or apps; restyle the portal by editing the tokens.
9. **Requesters are never asked questions; engineers approve.** For app requests, record ambiguities as assumptions (stricter option for approvals/PII), have an engineer approve the spec and its scenarios + journeys (as code, in a draft PR tracked by the portal's `/requests` dashboard) before building, then mark the built PR ready; CI records a video of every journey and the dashboard shows them. An Eng Lead pushes to production from the dashboard (merges the PR); Devin never merges. See `.agents/skills/build-internal-app/SKILL.md`.

## Before opening a PR
```
npm run check   # typecheck, lint, boundaries, validate-apps, catalog freshness, tests (incl. every app's src/apps/<slug>/scenarios.ts: scenarios + journeys), module-graph.json freshness
npm start & npm run smoke && npm run journeys   # page loads, then every journey played in the browser with a video each (journey-videos/)
npm run build
```
Regenerate `catalog.json` with `npm run catalog` whenever blocks/connectors/apps change.

## Skills

## Local run
`source ~/.nvm/nvm.sh && npm install && npm run seed && npm run dev` (Node ≥ 22.5 for `node:sqlite`). Switch users with the mock-SSO dropdown in the header.

## Module versions
Every block has a semver `version` in its manifest. `module-graph.json` (generated by `npm run graph`) records which files each block is built from and which block versions each app uses. If a PR changes any file a block is built from (including `src/blocks/_shared/`), bump that block's version: **major** if existing app configs could stop validating (option removed, newly required, type narrowed), **minor** for new optional options, **patch** otherwise. On a major bump, update every dependent app's config in the same PR. CI (`npm run graph -- --diff origin/main`) enforces the bump and lists affected apps. Apps always use the latest block version; never keep old copies of a block.
